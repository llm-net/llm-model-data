# 模型上下文长度维护

**新增模型与每次更新现有模型时，都必须查询本平台、本产品的官方上下文长度。** 价格、协议面或思考能力已核对，不能替代上下文核对；API 订阅与工具订阅也不能跳过。

## 字段与口径

- `capabilities.context_window_tokens`：本产品官方公布的上下文窗口，以整数 token 保存。默认记录常规窗口；扩展窗口、Max 模式、套餐或客户端版本条件写入 `context_assessment.notes`。仅存在有条件窗口时，可以记录该数值，但必须说明条件，不能表示所有用户都可使用。
- `capabilities.context_assessment.status`：`known` 已查明窗口；`partial` 已查到官方标称窗口但未确认精确整数边界；`unknown` 未能确认；`not_applicable` 当前图像 / 视频 / 语音生成接口没有适用的文本对话窗口。不能仅凭模型模态判不适用，需检查接口资料；文本模型不允许标不适用。
- `context_assessment.verification`：独立的 source ID、UTC 核对时间和本地 evidence。`known` / `partial` / `not_applicable` 需要核对证据；`unknown` 保持 `needs_review`、`checked_at=null`，证据记录尝试时间、来源与缺口；未知也必须有非空 source_ids 和本地 evidence，不能用空对象跳过查询。
- `context_assessment.reported_value`：官方窗口原始写法（如 `256K`、`1,000,000 tokens`）；known / partial 必填，unknown / not_applicable 为 null。
- `context_assessment.notes`：精确型号、产品范围、官方原始单位、换算方式、模式 / 套餐差异及未知原因。未知和不适用的数值均为 `null`，不能填 0、无限大或猜测值。

上下文窗口不等于最大输入、最大输出、思考预算、自动压缩阈值、字符数、TPM 或计费阶梯。`max_output_tokens` 仍单独保存，不从上下文长度相减推导。官方只公布最大输入时，不冒充总窗口；将该事实写入说明并继续查询。

优先采用官方整数 token 数。来源仅用 K / M 时，核对该平台的单位约定，保存原始写法与换算依据；不得全平台统一乘 1024，也不得凭型号名中的 128k / 1m 猜数值。只查到缩写规格而未确认精确整数时，`reported_value` 保存官方原始写法，状态 partial、新补数据的数值为 null；已有整数可保留但必须注明未能复核，消费者不能把 partial 的历史数值当成本轮确认；连窗口规格都未找到时才是 unknown。不能为了填整数而自行约定十进制或二进制。

## 每次更新步骤

1. 执行服务商和型号排除清单，列出本次所有新增及已有型号，包括日期版、短名和订阅模型。
2. 优先查官方模型 API / 机读目录，再查精确型号规格、接口文档及本产品套餐说明。聚合平台采用自己公布的限制；同名原厂 API、其他平台和开源权重配置都不能自动继承。
3. 核实普通 / 扩展模式、套餐、地区、协议或客户端版本是否改变窗口；区分总窗口、最大输入与最大输出，记录单位依据。短名的价格参考映射不证明窗口相同。
4. 在 `evidence/<provider>/` 记录 URL、UTC 获取时间、页面位置、逐模型结论及冲突。查询不到也要留下原因；网络失败不能刷新成功核对日期。
5. 填写窗口与独立 assessment。专项补上下文不改价格、协议面、思考能力及它们的核对日期；常规整批更新仍须同时执行各专项规范。
6. 运行 validate、单元测试和 review。检查上下文数值与条件的前后变化，报告必须持续列出全部 partial / unknown，包括本次未改的记录。已查到的数值不表示真实 Key 极限实测。

## 兼容与消费

`context_assessment` 是 v1 的可选元数据扩展，旧版本仍可按 schema 读取；当前仓库发布校验要求每个模型显式填写。消费者必须结合说明理解条件限制，不能把未知当作无限窗口。资料更新不等于消费者已接入或部署。
