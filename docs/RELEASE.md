# 数据版本发布约定

## 什么算正式发布

只有推送到本仓库 `origin` 的正式数据 tag 才表示发布。唯一命名格式：

```text
data-YYYY.MM.DD.N
```

- `YYYY.MM.DD`：北京时间（Asia/Shanghai）的实际发布日期，年月日固定为4/2/2位，必须是有效日历日期。
- `N`：当天发布序号，从1开始递增，不带前导零，不要求连续。
- 示例：`data-2026.09.16.1`、`data-2026.09.16.2`。
- 完整名称必须匹配 `^data-([0-9]{4})\.([0-9]{2})\.([0-9]{2})\.([1-9][0-9]*)$`，并额外验证日期有效。
- 不允许额外前后缀。`v1.0.0`、`latest`、`data-2026.09.16.01`、`data-2026.09.16.1-rc1`、无效日期都不算正式数据版本。

提交、推送main、仅在本地创建tag、创建GitHub Release说明，都不单独构成发布。数据内的`published`字段描述来源已有价格，不代表仓库正式发布。

## 如何判定最新发布

1. 读取远端tag清单，只保留上述格式和有效日期的tag；Git返回的`^{}`解引用记录不是独立tag。
2. 将年、月、日、序号转为整数，按`(年, 月, 日, N)`比较，最大的就是最新发布。比如同一天`.10`晚于`.9`，不能直接按字符串排序。
3. 不按提交时间、tag创建时间、推送时间、main最新提交或GitHub Release的“Latest”标记判断。
4. 没有符合规则的远端tag时，结果就是“尚无正式发布”，不得回退到main或其他命名的tag冒充正式版本。

发布者不得预打未来日期的正式tag；新发布版本号必须大于当前最新正式版本。版本日期不是模型官方调价生效日期，也不是格式的`schema_version`。

## 发布步骤

1. 按[人工确认流程](REVIEW.md)准备候选，完成数据校验、测试和差异审阅，取得针对该批内容的发布授权。已有明确授权且内容未变时不重复确认。
2. 将确认后的内容提交并推送到main。仅授权“提交、推送”时，到此结束。
3. 核对远端正式tag清单及目标提交，选择当日尚未使用且大于当前最新版本的序号。
4. 使用annotated tag（带说明的tag）指向main中确认过的**完整提交SHA**，说明写清变更和已知缺项；只推送这个tag。
5. 从远端核对tag解引用后的提交SHA与预期一致，报告版本号、提交和发布结果。

以下为命令形状，尖括号内容必须替换；不提供一键自动批准或发布命令：

```bash
git ls-remote --tags origin
git tag -a <data-YYYY.MM.DD.N> <已确认的完整提交SHA> -m "<变更摘要与已知缺项>"
git push origin refs/tags/<data-YYYY.MM.DD.N>
git ls-remote --tags origin
```

已推送的正式tag不得移动、覆盖或删除；更正数据发布新版本。回滚时消费者可指定旧版本；若要让所有跟随最新版本的消费者取得修正，发布版本号更高的修正版。

## 消费者约定与当前能力

云平台、盒子及其他消费者需要“最新发布”时，统一遵守上述筛选和排序规则，再解析tag所指向的提交读取数据；记录采用的tag和完整提交SHA，不直接跟随main。更新失败时保留已经采用的版本。

仓库发布与消费者生效独立：云平台核对并激活自己的价目，盒子更新自己的示意价格。发布tag不自动改变任何消费者。

当前已约定Git tag发布流程，仓库提供数据校验、审阅工具和校验CI；尚未实现自动打tag、消费者版本发现或同步，也未配置远端tag保护。上述不可覆盖要求目前是操作纪律，不是已经部署的强制门禁。无需另外搭发布服务或创建GitHub Release。
